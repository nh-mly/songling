# 遥操作 v2 方案 · 时间同步 / 空间同步 / 低延迟 / 力反馈

> 版本：v2.0 方案（在 v1.0 已验证的基础上）
> 现状：v1.0 已跑通（跨机位置遥操，稳态偏差 0.25°）
> 目标：把遥操从"能用"推进到"低延迟 + 可标定 + 可扩展到力反馈"

---

## 1. 目标与量化指标

| 需求 | 指标 | v1.0 现状 | v2 目标 |
|---|---|---|---|
| 时间同步 | 两机系统时钟偏差 | 未做 | **< 1 ms**（力反馈阶段 < 0.5 ms） |
| 空间同步 | 同姿态关节偏差 | 未标定（实测零位差最大 5.37°） | **< 1°** |
| 延迟 | A 动手 → B 电机响应，端到端 | 约 40–60 ms（未实测） | **< 30 ms** |
| 抖动 | 单向延迟 P95 − P50 | 未测 | WiFi < 20 ms / 有线 **< 1 ms** |
| 力反馈 | 反馈力带宽 / 稳定性 | 未做 | 100 Hz 带宽，无自激 |

## 2. v1.0 实测基线（作为对比依据）

### 2.1 跟随精度（70 秒拖动，28190 采样点）

| 指标 | 数值 |
|---|---|
| 静止时各关节平均偏差 | 0.06 ~ 1.85° |
| 最后 5 秒收敛偏差 | 全部 < 0.07° |
| 停下后收敛到 2° 内 | **24 ~ 26 ms** |
| 互相关最优滞后 | **0 采样（≈0 ms）** → 网络不是瓶颈 |

### 2.2 偏差与拖动速度的关系（关键发现）

| A 的拖动速度 | 平均偏差 |
|---|---|
| 0–50 °/s | **2.8°** |
| 50–100 °/s | 8.1° |
| 100–150 °/s | 13.7° |
| 150–200 °/s | 19.6° |
| 200–300 °/s | 20–25° |

**根因**：桥的指令上限 `max_step × rate = 3.0°/帧 × 50 Hz = 150 °/s`。
与网络无关（互相关滞后为 0），是**指令流的人为限速**。

### 2.3 两机零位差（必须标定的证据）

| 关节 | A | B | 差 |
|---|---|---|---|
| joint1 | +6.99° | +2.71° | 4.28° |
| joint2 | −0.23° | −0.19° | 0.04° |
| joint3 | −0.47° | −0.19° | 0.28° |
| joint4 | −11.67° | −7.80° | 3.87° |
| joint5 | +2.02° | −3.35° | **5.37°** |
| joint6 | +5.54° | +1.09° | 4.45° |

> 同为 v189 固件、同型号，零位仍差最多 5.37°。不做标定，力反馈时两台会"互相打架"。

## 3. 总体架构

### 3.1 五层

```
┌──────────────────────────────────────────────────────────┐
│ ⑤ 应用层   遥操作策略 · 状态机 · 安全监视 · 录制回放        │
├──────────────────────────────────────────────────────────┤
│ ④ 同步层   时钟同步(NTP/PTP) · 时间戳 · 延迟测量 · 插值     │
├──────────────────────────────────────────────────────────┤
│ ③ 传输层   DDS(有线优先) · QoS(best_effort/depth=1)        │
├──────────────────────────────────────────────────────────┤
│ ② 本地实时环  500~1000 Hz · A:阻抗/力 · B:位置+力估计      │
│             ★ 绝不跨网络 ★                                │
├──────────────────────────────────────────────────────────┤
│ ① 硬件层   CAN 1 Mbit · 6 轴 · MIT 模式(kp/kd/t_ff)        │
└──────────────────────────────────────────────────────────┘
```

### 3.2 核心原则

> **实时环在本地，同步层在中间，策略层在最上。**
> **跨网络只传"意图"（位置/力目标），不传"闭环"。**

### 3.3 为什么（闭环 vs 意图）

**v1.0 的做法——网络只传意图**：

```
【A 机】                【网络】              【B 机】
读关节角 ──────────────────────────► 收到目标位置
                                          │
                                ┌─────────▼──────────┐
                                │ B 的伺服内部闭环     │
                                │ 1 kHz，全部在本地    │
                                └────────────────────┘
```

网络只负责把目标送过去；B 怎么走到目标是 B 自己管的。
延迟只让动作"晚一点"，不影响稳定性。

> 类比：跟司机说"前面左转"。司机自己握方向盘（本地闭环）。
> 你这句话晚 1 秒，只是转弯晚 1 秒，不会失控。

**力反馈——网络变成闭环的一部分**：

```
        ┌───────────────── 网络 ─────────────────┐
        ▼                                        │
【B 测到外力 τ_ext】 ─► 【A 算反馈力矩】 ─► 【A 的电机出力】
        ▲                                        │
        └────── 【操作者的手 → A 的位置】 ◄────────┘
```

网络在环内：任何延迟/抖动都直接变成控制问题。

> 类比：蒙眼握方向盘，有人电话指挥"偏左了"。
> 延迟固定还能适应；**延迟乱跳就会过度修正，来回摆**。

### 3.4 因此，两边必须各自闭环

```
【A 本地 500~1000 Hz】      【网络 200 Hz】      【B 本地 500~1000 Hz】
阻抗环:                      只传参考值:           位置环:
τ = kp(p_des−p) + τ_ff  ──►  p_des  ─────────►   追踪 p_des
     ▲                     ◄──  τ_ext  ◄──────    估外力
     └───────────────────────────────────────
```

延迟的作用退化为"参考值晚到"→ 响应变慢，但**不发散**。

## 4. 网络方案

### 4.1 现状：同一局域网（WiFi）

```
无线路由器
├── A 机  192.168.3.232
└── B 机  192.168.3.179
```

`ROS_DOMAIN_ID=66` + `ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET`，DDS 走 UDP。

### 4.2 关键概念：换的不是"网络"，是"物理介质"

"同一个局域网"不变，只换中间那一段：

| 方式 | 数据路径 | 延迟 | 抖动 |
|---|---|---|---|
| **WiFi（现在）** | A → 无线路由器 → B | 3–8 ms | **±10~50 ms** |
| **有线** | A → 网线 → 交换机 → 网线 → B | 0.2–0.5 ms | **±0.1 ms** |

**WiFi 抖动三个来源**：

1. 空口竞争——同信道设备轮流发言，别人传大文件你就得等
2. 重传——无线丢包常态 1–5%，每次重传 +5~20 ms
3. 速率自适应——信号弱时 AP 降速率，延迟突变

有线没有这三个问题：交换机转发是硬件级，稳定在 0.1 ms 量级。

### 4.3 分阶段是否够用

| 用途 | WiFi |
|---|---|
| 位置遥操（v1.0/v1.1） | ✅ 够 |
| chrony 时间同步 | ⚠️ 勉强（2–5 ms） |
| **力反馈（v2.x）** | ❌ **不够**，必须换有线 |

### 4.4 换有线的方式（不影响代码）

1. 两根网线接到同一路由器/交换机的 LAN 口
2. IP 自动同网段（DHCP）或设静态
3. **`ROS_DOMAIN_ID=66` 与 `SUBNET` 均不需要改**
4. 代码零改动

## 5. 时间同步方案

### 5.1 三种可选

| 方案 | 精度 | 硬件要求 | 适用阶段 |
|---|---|---|---|
| **chrony (NTP)** | WiFi 2–5 ms / 有线 0.2–1 ms | 无 | v1.1 |
| **PTP (IEEE 1588)** | µs 级 | 网卡支持硬件时间戳 + 有线 | v2.0 |
| GPS/北斗 | µs 级 | 接收模块 | 跨楼场景 |

### 5.2 v1.1：chrony（先做这个）

**A 机（时间源）**

```bash
sudo apt install -y chrony
sudo tee -a /etc/chrony/chrony.conf <<'EOF'
# 作为局域网时间源
allow 192.168.3.0/24
local stratum 10
EOF
sudo systemctl restart chrony
```

**B 机（跟随）**

```bash
sudo apt install -y chrony
sudo sed -i '1i server 192.168.3.232 iburst prefer' /etc/chrony/chrony.conf
sudo systemctl restart chrony
chronyc tracking        # 看 System time 偏差
```

**验收**：`chronyc tracking` 的 offset < 1 ms，且 5 分钟内不漂。

### 5.3 v2.0：PTP（做力反馈前）

```bash
sudo apt install -y linuxptp
# 需要网卡支持硬件时间戳，先用 ethtool 确认
sudo ethtool -T eth0 | grep -i hardware
```

要求：**必须千兆有线**，WiFi 下 PTP 不可靠（无硬件时间戳）。

### 5.4 ROS 2 侧配合

| 项 | 做法 |
|---|---|
| 时钟源 | `use_sim_time:=false`（用已同步的系统时钟） |
| 时间戳 | 每条消息 `header.stamp = now()` |
| 验证 | 双向 ping-pong 测 RTT，检查对称性 |

### 5.5 时间戳的三个用途

1. **延迟测量**：B 收到时 `now() - msg.stamp`
2. **插值/外推**：帧不齐时按时间戳插值，而不是"用最新帧"
3. **录制回放**：两机轨迹按同一时基对齐

## 6. 延迟预算与优化

### 6.1 v1.0 的延迟分解（估算）

| 环节 | 耗时 | 可优化 |
|---|---|---|
| CAN 读 → 驱动发布 | 5 ms | 已是 200 Hz |
| DDS / WiFi | 2–5 ms | 换有线 → 0.5 ms |
| **桥（50 Hz + 低通）** | **20–30 ms** | ★ 最大瓶颈 |
| CAN 写 → 电机响应 | 10–20 ms | 提高 speed_percent |
| **合计** | **40–60 ms** | |

### 6.2 优化清单（按收益排序）

| 优化 | 收益 | 代价 |
|---|---|---|
| **桥 50 Hz → 200 Hz** | −15 ms | 流量 ×4（仍 < 200 KB/s） |
| **去低通 `alpha=1.0`** | −10 ms | 需用死区代替噪声抑制 |
| **换千兆有线** | −3 ms，**抖动 ±10 ms → ±0.1 ms** | 布线 |
| QoS 改 `best_effort` + `depth=1` | −1~2 ms | 丢帧不重传（遥操可接受） |
| `speed_percent` 提到 100 | −5~10 ms | 撞击风险，需额外限速 |
| CPU 隔离 + `SCHED_FIFO` | 减少抖动 | 需 root |

**目标**：桥 200 Hz + 有线 + best_effort → **端到端 < 25 ms**。

### 6.3 反直觉结论

> **抖动比平均延迟更重要。**
>
> 稳定 40 ms：操作者能适应。
> 20~80 ms 抖动：手感"迟滞、发飘"，无法精细操作。

所以优先顺序是 **换有线（降抖动）> 提频率（降延迟）**。

## 7. 空间同步方案

### 7.1 误差来源

| 来源 | 量级 | 可否消除 |
|---|---|---|
| 关节零点偏差 | 0.1–1°（实测最大 5.37°） | ✅ 标定 |
| 连杆加工误差 | < 1 mm | ⚠️ 需末端标定 |
| 谐波减速器滞回 | 0.1–0.5° | ❌ 只能减小 |
| 温漂 | 0.1–0.3°/h | ⚠️ 定期重标 |
| 伺服跟踪误差 | 0.05–0.2° | ❌ |

### 7.2 三级标定

#### 级 1 · 零点标定（必做，10 分钟）

```
两台 move_home → 各采样 100 次取均值 → offset[i] = mean(leader[i]) − mean(follower[i])
```

写入 `teleop_params.yaml` 的 `joint_offset_deg`。

#### 级 2 · 多点最小二乘（推荐，1 小时）

拖到 8–12 个分散姿态，每个姿态停 2 秒采集：

```
follower[i] = a[i] × leader[i] + b[i]
```

- `a[i]` 修正连杆长度差异（比例项）
- `b[i]` 修正零点（偏置项）

#### 级 3 · 末端验证

用桌面上的已知点（如锥尖）接触验证，比较两台末端偏差。

### 7.3 关节映射的固有局限

**同样的关节角，末端位置可能差几毫米**（连杆加工误差导致）。

如果要求末端精确一致，必须改成笛卡尔映射：

```
A 关节角 → FK → A 末端位姿 → 加偏移 → B 的 IK → B 关节角
```

**但力反馈场景不建议走笛卡尔映射**：IK 数值解在小范围会跳，抖动会直接变成力抖动，破坏稳定性。

**结论**：空间同步用"关节映射 + 标定"，接受 5–10 mm 的末端偏差。

## 8. 力反馈架构

### 8.1 硬件能力确认（已核实）

| 能力 | 接口 | 状态 |
|---|---|---|
| MIT 阻抗模式 | `move_mit(joint, p_des, v_des, kp, kd, t_ff)` | ✅ SDK 支持（单关节） |
| 力矩反馈 | `/feedback/joint_states` 的 `effort`（= `ms.msg.torque`） | ✅ 驱动已发布 |
| 电机状态 | `get_motor_states(joint)` | ✅ SDK 支持 |

**结论：硬件层面支持双边力控，不需要额外硬件。**

### 8.2 控制架构：力-位置（force-position）

```
┌─ A 侧（leader，人操作）──────────────────────────┐
│  阻抗控制:                                        │
│    τ_ff = τ_feedback + kp_h·(p_des − p)          │
│    kp_h 很低(0.5~2)，手臂"柔软"                    │
│  输出: p_leader（操作者拖到的位置）                 │
│  输入: τ_feedback（来自 B 的外力估计）              │
└──────────────────────┬───────────────────────────┘
                       │ p_leader  (200 Hz)
                       ▼
                 ═══ 网络（延迟 d，抖动 j）═══
                       │
┌─ B 侧（follower，执行）──────────────────────────┐
│  位置控制: p_des = p_leader                       │
│  外力估计: τ_ext = τ_motor − τ_grav − τ_fric      │
│  输出: τ_ext (100 Hz 回传)                        │
└──────────────────────────────────────────────────┘
```

### 8.3 三个必须解决的技术问题

#### 问题 1 · 外力估计

```
τ_ext = τ_motor − τ_gravity(q) − τ_friction(q̇)
```

| 项 | 来源 |
|---|---|
| τ_motor | `/feedback/joint_states` 的 effort |
| τ_gravity | URDF 质量参数正动力学（需标定质量/质心） |
| τ_friction | 库仑+粘滞模型（需离线实验标定） |

**难点**：摩擦标定需单独做实验（低速扫掠测力-速曲线）。误差会变成"假力"传回操作者手上。

#### 问题 2 · 稳定性（最关键）

带延迟的双边力控**天然不稳定**。粗略稳定边界：

```
d_max ≈ √(J / K)
```

取腕部 `J ≈ 0.1 kg·m²`，目标刚度 `K = 50 N·m/rad`：

```
d_max ≈ √(0.1/50) = 0.045 s = 45 ms
```

| 网络 | 典型延迟 | 抖动 | 结果 |
|---|---|---|---|
| WiFi | 3–8 ms | ±10~50 ms（峰值 60–100 ms） | ❌ 自激 |
| 有线 | 0.2–0.5 ms | ±0.1 ms | ✅ 稳定 |

三条稳定化路线：

| 方法 | 原理 | 复杂度 | 延迟容忍 |
|---|---|---|---|
| 加阻尼 + 限幅 | 粗暴但有效 | ⭐ | < 20 ms |
| **波变量（wave variables）** | 力/速度变"波"，保证无源 | ⭐⭐⭐ | 50–200 ms |
| 时间域无源性（TDPA） | 监测能量，超限耗散 | ⭐⭐⭐ | 50–300 ms |

**路线**：先用"阻尼+限幅"验证手感，稳定后再上波变量。

#### 问题 3 · CAN 带宽

`move_mit` 是**单关节**接口，6 轴 = 6 帧/周期：

```
1 kHz × 6 = 6000 帧/s，CAN 1 Mbit ≈ 7700 帧/s → 接近饱和
```

**实际建议频率**：

| 环节 | 频率 |
|---|---|
| B 侧位置环 | 500 Hz |
| 力回传 | 100–200 Hz |
| A 侧阻抗环 | 500 Hz |

不需要真的 1 kHz。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| WiFi 抖动 | 力控不稳 | 换有线（硬前提） |
| 摩擦模型不准 | 手感粘滞、假力 | 离线标定 + 低速段单独处理 |
| 重力补偿不准 | 静止时"飘" | URDF 质量 + 实测修正 |
| 波变量实现错误 | 系统反而震荡 | 离线仿真验证后再上真机 |
| CAN 饱和 | 掉帧、不同步 | 限 500 Hz，或确认固件是否支持批量 MIT |
| 力反馈伤人 | 安全事故 | 力限幅、急停、deadman 开关 |
| 零位漂移 | 长时间后偏差变大 | 定期重标（每次开机做级 1） |

## 12. 明确不做

| 不做 | 原因 |
|---|---|
| 笛卡尔空间映射 | IK 抖动会破坏力反馈稳定性 |
| 真正的 1 kHz 全关节 MIT | CAN 带宽接近饱和，收益不明确 |
| 视频遥操回传 | 另立项目，与力控无关 |
| 跨公网 / 4G 遥操 | 延迟不可控，只能做监控不能做力控 |

## 13. 优先级建议

```
1. 换有线 + chrony          ← 一天见效，所有后续工作的基础
2. 桥提速到 200 Hz          ← 延迟立降 15 ms
3. 空间标定                 ← 消除 5.37° 的 j5 偏差
4. 力反馈                   ← 前 3 步做完再开始
```

**顺序不能乱**：

- 没时钟同步 → 测不出延迟，优化无从下手
- 没低延迟 → 力反馈必然震荡
- 没空间标定 → 力反馈时两台姿态不一致，力会互相"打架"
