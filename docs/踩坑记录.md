## 1. 同网段的另一台机器会污染你的 ROS 图

**现象**:RViz 一起就崩

```
[ERROR] Variable 'joint7' is not known to model 'agx_arm'
terminate called after throwing an instance of 'moveit::Exception'
```

**诊断**:

```
不隔离 → /joint_states 发布者 = piper_driver,内容 joint1…joint8(8 个)
隔离   → piper_driver 消失,/joint_states 不存在
```

**原因**:ROS 2 DDS 默认跨机发现。实验室另一台机器跑着 Piper 驱动,往同一个
`/joint_states` 发 8 关节状态;我们的模型只有 6 轴,joint7 无对应 → RViz 抛异常退出。

**更严重的**:那台 `piper_driver` **订阅 `/control/joint_states`** —— 我们 MoveIt 下发
指令的话题。跑 mock 期间,我们的关节指令一直在往它那里发。如果那台臂处于使能状态,
它可能真的动了。

**对策**:
```bash
export ROS_DOMAIN_ID=42
export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST
```
已写进 `scripts/env.sh`。

## 4. `goal_constraints` 是"目标区域列表"(OR),不是"条件列表"(AND)

**现象**:发了 joint1=0.6 / joint2=0.5 / joint3=-0.4,执行返回 SUCCESS,
但 joint2 落在 2.405。

**原因**:三个关节被拆成三个 `Constraints` 塞进 `goal_constraints`,
规划器只要满足**任意一个**就算成功。

**正确写法**:
```python
cons = Constraints()
for name, val in targets.items():
    jc = JointConstraint(); jc.joint_name = name; jc.position = val
    jc.tolerance_above = 0.02; jc.tolerance_below = 0.02; jc.weight = 1.0
    cons.joint_constraints.append(jc)
goal.request.goal_constraints.append(cons)      # 只放一个区域
```


## 16. `--tcp 0` 与 TCP 坐标混用 → 夹爪戳进桌面

**现象**：手臂撞到桌面。

**原因**：`move_to --xyz` 的语义取决于 `--tcp`：

```
--tcp 0       → xyz 是「法兰」坐标
--tcp 0.1425  → xyz 是「TCP(指尖)」坐标
```

撞桌那次给的是**法兰** z=0.129，而工具朝下时指尖比法兰低 142.5 mm：

```
法兰 z = 0.129
指尖 z = 0.129 - 0.1425 = -0.013   ← 已在桌面以下
```

**规则**：
- 用 `--tcp`(默认 0.1425)时，`--xyz` 给指尖，**指尖 z ≥ 0.01**
- 用 `--tcp 0` 时，`--xyz` 给法兰，**法兰 z ≥ 0.16**
- 看 dry-run 打印的 `→ 法兰 (...)` 那行，法兰 z < 0.16 就别执行

## 17. 「工具朝下」的 rpy 是 `0 180 0`，不是 `180 0 0`

`180 0 0` 是**绕 X 轴滚转 180°**，工具轴仍在水平面内。

用 `180 0 0` 当"朝下"时，可达性地图整片为空（IK 全 -31），排查了半天才发现是参数错。

**记法**：`rpy = (roll, pitch, yaw)`，朝下是把 pitch 转 180°。

## 18. 真机零位略超 URDF 限位 → `follow:=true` 时所有规划被拒

**现象**：`move_to` 全部返回 `error_code=99999`，连当前位姿都规划不出来。
切到 `follow:=false` 立刻恢复正常。

**原因**：真机 `joint2 = -0.01°`，而 URDF 限位是 `[0°, 180°]`。
`follow:=true` 时 move_group 用真机反馈当起始状态 → 判定越界 → 拒绝一切规划。

**修法**：把 URDF 的边界放宽 2°（真机零位本来就有小偏差）：

```xml
<!-- piper_description.urdf -->
joint2: lower 0        → -0.0349066   (-2°)
joint3: upper 0        → +0.0349066   (+2°)
```

改完重编 `agx_arm_description` 即可。备份在同目录 `piper_description.urdf.bak-limits`。

## 19. 规划场景里默认没有桌子

撞桌的直接原因不是"规划错了"，而是**规划器根本不知道桌子存在**——场景里只有机械臂自己。

**修法**：往场景加一个碰撞物体

```python
obj.header.frame_id = "base_link"
obj.id = "table"
# 1.2×1.2 m 板,顶面 z=0,厚 50 mm
```

加完之后撞桌的位姿会被判定为碰撞，规划直接失败而不是撞上去。

**注意**：规划场景在 move_group 内存里，**重启就丢**。要持久化得写进 launch。

## 20. 门闸状态读不出来：`ros2 param get` 永远是 False

驱动里 `control_enable` 的服务回调只改 Python 属性：

```python
self.control_enabled = request.data      # 改了属性
# 没有 self.set_parameters(...)         # 参数没变
```

所以 `ros2 param get ... control_enabled` 永远显示启动时的值，**不能用来判断门闸是否打开**。

**判断方法**：看驱动日志里的 `External control gate opened/closed`。

## 21. MoveIt 在跑时，往话题发指令会被覆盖

`joint_state_broadcaster` 以 `pub_rate`(默认 200 Hz) 持续往 `/control/joint_states` 发 mock 状态。
手动 `ros2 topic pub` 的指令会被这些消息冲掉——**看起来"发了但没动"**。

**规则**：

| 场景 | 正确做法 |
|---|---|
| MoveIt 在跑 | 走控制器 action(`gripper_controller` / `arm_controller`)，或用 `scripts/grip.sh` |
| MoveIt 没跑 | 可以直接发话题(需先 `control_enable true`) |

## 22. `move_home` 一次可能不到位

从大姿态回零时，`move_home` 有时只走到一半（例如 j5 停在 22°），日志仍打印
`Agx_arm moved to home position successfully`。

原因是 `_wait_motion_done()` 把"当前没在动"当成"已到位"。

**做法**：回零后必须读一次角度确认；不是全 0 就再调一次。

## 23. 碰撞之后驱动内部状态会乱

撞桌之后出现过：
- `move_home` 报成功但角度不动
- 关节反馈在两个姿态之间跳变
- 手动 jog 完全没反应

**修法**：不要试图原地恢复，**干净重启**：

```bash
# 杀掉所有 ROS 进程
pkill -x rviz2; pkill -x move_group; pkill -x ros2_control_node; pkill -x robot_state_publisher
pkill -f 'agx_arm_ctrl_single_node'
# 重新起驱动 → 使能 → 回零
```

重启后 `move_home` 一次到位。

## 25. MJCF 的关节名和 URDF 不一致

`agx_arm_sim` 的 `piper.xml` 里，夹爪叫 **`joint7` / `joint8`**（两个手指，用 `<equality>` 联动），
而我们的 URDF/SRDF 叫 **`gripper`**（+ `gripper_joint1/2`）。

直接拿来用，ros2_control 暴露 `joint7`，MoveIt 的控制器映射找不到 `gripper`。

**改法**（复制一份 MJCF，不动原仓库）：

```xml
<joint name="joint7" ...>          → <joint name="gripper" ...>
<joint joint1="joint8" joint2="joint7" ...> → joint2="gripper"
<position name="gripper" joint="joint7" ...> → joint="gripper"
```

另外行程也对齐：MJCF 是 70 mm 档（`0.035`/边），URDF 是 100 mm（`0.05`/边），
改成 `0.05` 两边才一致。

> `joint8` 不用改名，它没有对应 actuator，ros2_control 会当 passive joint 处理，
> 由 MJCF 的 `<equality>` 约束跟着 `gripper` 动。

## 26. 静态 SRDF 里没有 `disable_collisions` → 零位就报自碰撞

**现象**：

```
[ERROR] PlanningRequestAdapter 'CheckStartStateCollision' failed,
        because '3 contact(s) detected : link1 - link2, link2 - link3, link3 - link4'
```

零位规划直接失败（`error_code=-10`）。

**原因**：`install/agx_arm_moveit/share/agx_arm_moveit/config/agx_arm.srdf` 里
**`disable_collisions` 是 0 条**。相邻连杆在模型里本来就有接触，必须显式禁用。

而 `agx_arm.srdf.xacro` 展开后是 **23 条**。

**改法**：用 xacro 生成 SRDF，而不是读静态文件

```python
srdf_xml = Command([xacro, ".../agx_arm.srdf.xacro",
                    " arm_type:=piper effector_type:=agx_gripper"]).perform(context)
# 作为 robot_description_semantic 传给 move_group 和 rviz
```

## 27. `moveit_controllers.yaml` 的键必须平铺到顶层

**现象**：`[ERROR] simple_controller_manager: No controller_names specified.` → `Returned 0 controllers` → 执行报 `CONTROL_FAILED (-4)`

**原因**：`MoveItConfigsBuilder.to_dict()` 是把 `trajectory_execution` 的内容**平铺**到参数顶层，
不是塞在 `moveit_controllers:` 下面。

**错**：
```python
{"moveit_controllers": yaml.safe_load(f)}
```
**对**：
```python
dict(yaml.safe_load(f))     # moveit_controller_manager + moveit_simple_controller_manager 两个顶层键
```

## 28. `MoveItConfigsBuilder` 默认的 URDF 没有夹爪

`agx_arm_moveit/config/agx_arm.urdf.xacro` 开头：

```xml
<xacro:arg name="effector_type" default="none" />
```

默认 `none` → 展开出 6 个关节，**没有 gripper**。
于是仿真里有夹爪、RViz 里没有，MoveIt 还会报 `Failed to add group 'gripper'`。

**改法**：给 `move_group` 和 `rviz2` 显式传自己的 URDF（带 `with_gripper` 的那份），
SRDF 也要用 `effector_type:=agx_gripper` 展开，两者必须匹配。

**验证**：
```bash
ros2 param get /move_group robot_description | grep -c 'name="gripper"'   # 应为 2
```

## 29. launch 里 `emulate_tty=True` 可能耗尽 pty

**现象**：`OSError: out of pty devices`，节点起不来。

沙箱/容器里 pty 数量有限，多个 `emulate_tty=True` 的节点会把它用光。

**改法**：去掉 `emulate_tty=True`（默认 False 即可）。

## 30. 多套 ROS 栈并存会互相抢 controller_manager

调试时同时开着真机驱动、MoveIt mock、MuJoCo，会发现控制器全是 `inactive`。

**原因**：多个 `controller_manager` 在同一 domain 上抢服务与话题。

**做法**：换栈之前先彻底清场

```bash
python3 - <<'PY'
import os, signal
me, parent = os.getpid(), os.getppid()
A, B = '/opt/ros/' + 'jazzy', '/home/nero/107/songlin/' + 'install'
for pid in os.listdir('/proc'):
    if not pid.isdigit(): continue
    p = int(pid)
    if p in (me, parent): continue
    try: cmd = open(f'/proc/{pid}/cmdline','rb').read().replace(b'\0',b' ').decode(errors='ignore')
    except Exception: continue
    if A in cmd or B in cmd:
        try: os.kill(p, signal.SIGKILL)
        except Exception: pass
PY
```

> 注意：`pkill -f 'xxx'` 经常把发起命令的 shell 自己也匹配掉（命令行里含同样的字符串），
> 上面这种"读 /proc 再按 PID 杀"更安全。
